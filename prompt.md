## 1. REPOSITORY INTEGRATION — NON-NEGOTIABLE

Before modifying code, inspect the repository and identify:

1. The current application structure.
2. The active route or entry point for the marketing site.
3. The package manager already in use.
4. Existing UI primitives and reusable components.
5. Existing layout/container components.
6. The current icon solution.
7. Existing typography, radius, spacing, shadow, border, and motion conventions.
8. Existing CSS variables and semantic Tailwind utilities defined through the repository's global CSS and Tailwind v4 configuration.
9. Existing light/dark theme behavior.
10. Existing lint, format, type-check, test, and build commands.

### Mandatory repository rules

- Do not replace the existing framework, renderer, router, bundler, package manager, or project structure.
- Do not migrate the repository to another stack.
- Do not rewrite configuration files without a real implementation need.
- Do not overwrite or redesign the color system in global.css.
- Do not introduce a second design system.
- Do not create a parallel set of color variables.
- Do not hardcode hexadecimal, RGB, HSL, OKLCH, or named palette colors in page components.
- Do not use arbitrary Tailwind color values.
- Use the repository's existing semantic tokens and utilities for background, surface, text, muted text, border, accent, ring, destructive, success, warning, and chart colors.
- If token names differ from common conventions, adapt to the repository instead of forcing new names.
- Preserve existing brand assets, font loading, theme behavior, and global styles.
- Reuse existing native UI primitives before creating new ones.
- New components must compose the existing primitives rather than duplicate them.
- Do not add a dependency when the same result can be achieved with the repository's current dependencies.
- Framer Motion is explicitly allowed for animation. Use it as the only dedicated animation dependency.

If the repository already contains a product name, logo, navigation model, contact route, demo route, or authentication route, use those values. Use Nexus ERP only as a fallback when the repository does not define a brand name.

## 8. MOTION SYSTEM — FRAMER MOTION

Use Framer Motion with restraint and purpose.

### Motion principles

- Motion explains hierarchy, state change, or relationship.
- Motion must never compensate for weak composition.
- Do not animate every element.
- Avoid constant movement.
- Avoid scroll hijacking.
- Avoid large parallax movements.
- Avoid cursor-following decorative effects.
- Avoid springy consumer-app motion in enterprise contexts.

### Shared motion primitives

Create reusable variants or helpers for:

- section reveal
- child stagger
- subtle blur-to-sharp reveal
- state crossfade
- panel enter/exit
- metric value transition
- list item insert/update

Use centralized duration and easing constants. Prefer the repository's existing motion tokens when available.

### Required reduced-motion behavior

- Respect prefers-reduced-motion.
- Remove translation, blur, and stagger when reduced motion is enabled.
- Preserve state changes without animation.
- Never hide important content behind animation completion.

### Section motion map

- Header: border/surface transition on scroll.
- Hero: coordinated initial reveal and controlled state transitions.
- Trust rail: subtle metadata disclosure.
- Problem map: staged connector reveal.
- Lifecycle: selected-stage transition.
- Module explorer: contextual preview crossfade.
- Product workspace: mode and data transitions.
- Capabilities: localized state transitions only.
- Security: layer highlight.
- Analytics: chart update transition.
- Testimonials: manual crossfade.
- FAQ: height and opacity transition through the existing primitive.
- Final CTA: one restrained reveal.

Do not add animated gradients.
